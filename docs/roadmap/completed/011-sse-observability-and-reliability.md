## Результат

Пользователь может проверить endpoint до сохранения, понять причину разрыва и
увидеть состояние повторного подключения без чтения внутренних логов.

## Проблема

Retry и lifecycle уже реализованы, но диагностика преимущественно остаётся в
логах. Ошибки URL, TLS, авторизации, HTTP status и формата SSE выглядят для
пользователя слишком похоже.

## Объём работ

1. Добавить безопасную команду проверки соединения без сохранения конфигурации.
2. Ввести нормализованные категории ошибок: configuration, DNS/network, TLS,
   authentication, HTTP, protocol и cancelled.
3. Показывать attempt, время следующего retry и итоговое terminal state.
4. Обеспечить немедленную отмену connect/retry при disable/delete/shutdown.
5. Добавить correlation id соединения в логи без token и полного query string.
6. Реализовать экспорт диагностического пакета с явным allowlist полей.
7. Добавить локальный SSE fixture для happy path, malformed events, disconnect,
   timeout, authentication failure и cancellation.

## Не входит

- Полная история сообщений.
- Удалённая телеметрия и автоматическая отправка логов.
- Изменение протокола сервера.

## Приёмка

- Проверка endpoint не создаёт постоянное соединение и не меняет settings.
- Пользователь видит различимые и пригодные к действию ошибки.
- Retry state соответствует фактическому backend lifecycle.
- После cancel/delete не остаётся фоновой попытки и stale UI update.
- Диагностический export не содержит token/cookie и пользовательский текст по
  умолчанию.

## Верификация

- Rust integration tests с локальным SSE fixture;
- fake-time tests backoff/cancellation;
- frontend tests отображения состояний;
- ручные сценарии: offline, неверный host, 401/403, 500, malformed SSE и
  восстановление сервера.

### Ключевые решения

- **Таксономия ошибок** (task 001): ровно 7 категорий из объёма работ —
  `configuration / network / tls / authentication / http / protocol / cancelled`
  (`connections/error.rs`, serde snake_case). Классификация — по текстам ошибок
  eventsource-client 0.12/hyper в одной функции с консервативным фолбэком в
  `network`; категория `http`/`authentication` достижима через маркеры
  `unexpected response: {status}`, подтверждено fixture-тестом на реальном 401.
- **Статусная поверхность** (task 002): payload `connection-status-changed`
  стал структурным JSON `{id, status, errorKind?, errorMessage?, attempt?,
  maxAttempts?, nextRetryInSecs?}`; между попытками эмитится `Retrying`
  (вместо голого Disconnected), при исчерпании бюджета — терминальный
  `Error{kind, message}` с фиксированным текстом. Snapshot-DTO отдаёт те же
  поля.
- **Отмена** (task 004): кооперативный cancellation-token (tokio watch) на
  подключение + `abort()`-backstop; после отмены задача не эмитит ни одного
  события. Отмена при disable (через update), delete, disconnect и shutdown
  (`stop_all` на `RunEvent::Exit`); `connect` для disabled — no-op без
  события Connecting (закрыта дыра baseline).
- **Таймаут попытки** (task 006): добавлен таймаут «до первого события» 10с —
  молчащий сервер не держит попытку вечно; классифицируется как network.
- **Ретрай-политика**: сохранена прежняя (5с × 10, предсказуемость);
  exponential backoff — вне объёма, потенциальный фоллоу-ап.
- **Экспорт диагностики** (task 008): явная allowlist-структура (версия, ОС/арх,
  по подключению id/санитизованный URL/enabled/статус/errorKind/attempt-поля/
  isTyping, сводка не-секретных настроек), атомарная запись в
  `%APPDATA%/ttsbard-echo/diagnostics/`, кнопка в панели. Имя подключения,
  last_message, preview_text и токен (в любой форме) в экспорт не читаются
  вовсе.

### Известные ограничения / фоллоу-апы

- Классификация опирается на тексты ошибок крейта — при обновлении
  eventsource-client паттерни нужно перепроверить (тесты fixture фиксируют
  фактические тексты).
- Ретрай-цикл не различает «бессмысленные» категории (401/500 ретраятся до
  исчерпания бюджета) — возможный фоллоу-ап.
