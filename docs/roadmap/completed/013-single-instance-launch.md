# 013 — Один экземпляр и повторный запуск

- **Статус:** completed
- **Приоритет:** P1
- **Зависимости:** 008, 009, 010, 011
- **Источник паттерна:** `app-tts-v2`, ROADMAP-092 и `src-tauri/src/single_instance.rs`

## Цель

В одном сеансе Windows работает только один экземпляр Echo, а повторный запуск
через EXE, ярлык или меню «Пуск» показывает и активирует главное окно уже
работающего процесса, не сбрасывая подключения и текущие сообщения.

## Почему это нужно Echo

Главное окно Echo закрывается скрытием в tray, поэтому пользователь может
принять скрытое приложение за завершённое и запустить вторую копию, которая
начнёт параллельно читать и записывать те же настройки и откроет повторные SSE
подключения.

## Эталон из app-tts-v2

ROADMAP-092 прошёл от готового Tauri plugin к собственному Windows-модулю:

- именованный mutex ограничивает экземпляр текущим Windows-сеансом;
- guard вызывается первой операцией `run()`, до логов, настроек и Tauri builder;
- скрытое top-level окно принимает команду показа через `WM_COPYDATA`;
- второй процесс ищет приёмник и отправляет запрос с общим таймаутом 10 секунд;
- `SendMessageTimeoutW(SMTO_ABORTIFHUNG)` не позволяет зависшему первому
  процессу навсегда удержать повторный запуск;
- подтверждение wndproc отличает принятую команду от формально успешной отправки;
- запрос, пришедший до готовности Tauri main window, запоминается и выполняется
  после регистрации callback;
- mutex удерживается handle процесса и автоматически освобождается Windows
  после штатного или аварийного завершения;
- невозможность создать guard/receiver или связаться с первым процессом
  завершается явной ошибкой, а не запуском второй рабочей копии.

Готовый `tauri-plugin-single-instance` не переносится автоматически: в
эталонном проекте он был отклонён, потому что получает lock только во время
plugin setup и не защищает раннюю инициализацию до Tauri builder.

## Согласованное поведение Echo

| Состояние первого экземпляра | Повторный запуск |
|---|---|
| Главное окно открыто | Активировать и перевести в фокус |
| Главное окно свёрнуто | Развернуть, показать и активировать |
| Главное окно скрыто в tray | Показать и активировать |
| Backend ещё запускается | Дождаться receiver, принять запрос и показать окно после готовности callback |
| Первый процесс завис и не подтверждает запрос | Показать нативную ошибку и завершить второй процесс с ненулевым кодом |

Повторный запуск никогда не должен переключать уже видимое окно в скрытое
состояние, создавать вторые SSE-задачи или изменять настройки.

## Объём работ

### 1. Общая операция показа главного окна

- Выделить `show_main_window(app_handle, source)` как единственный путь показа.
- Если окно свёрнуто — вызвать `unminimize`, затем `show` и `set_focus`.
- Перевести tray click и tray menu «Показать» на этот helper.
- Ошибки операций логировать с источником (`tray-click`, `tray-menu`,
  `second-instance`), не превращая повторный запрос в toggle.

### 2. Ранний Windows single-instance guard

- Добавить `src-tauri/src/single_instance.rs` под `#[cfg(windows)]`.
- Использовать уникальные имена Echo, производные от `com.ttsbard.echo`, а не
  имена TTSBard из эталонного проекта.
- Вызвать `acquire_lock_or_exit()` первой строкой `run()`, до `init_logging()`.
- Первый процесс создаёт mutex и receiver window; второй только доставляет
  команду и завершается.
- Не использовать lock-файл: после crash не должна требоваться ручная очистка.

### 3. Доставка команды показа

- Receiver принимает только собственный тип `WM_COPYDATA` и возвращает явное
  подтверждение.
- Discovery receiver и доставка используют один ограниченный бюджет 10 секунд.
- Между созданием mutex и receiver второй процесс повторяет поиск с коротким
  интервалом, закрывая startup race.
- Для сочетания обычного и повышенного запуска разрешить сообщение через
  `ChangeWindowMessageFilterEx`; отказ не разрешает запуск второй копии.
- Сообщения об ошибке должны называться Echo и быть доступны в release без
  консоли через нативный `MessageBoxW`.

### 4. Регистрация callback после готовности Tauri

- Зарегистрировать callback после создания main window и доступности
  `AppHandle`, но до объявления setup полностью завершённым.
- Если receiver уже принял запрос, выполнить отложенный показ сразу после
  регистрации.
- Callback не читает settings и не запускает backend повторно; он только
  вызывает общий `show_main_window`.

### 5. Windows API и документация

- Расширить features существующей зависимости `windows` только необходимыми
  namespace: DataExchange, LibraryLoader и WindowsAndMessaging.
- Описать повторный запуск и способ полного выхода в пользовательской
  инструкции.
- Добавить single-instance module и startup order в архитектурную документацию.

## Не входит

- Изменение текущего поведения крестика: главное окно продолжает скрываться в tray.
- Новая настройка minimize-to-tray или hide-on-minimize.
- Изменение поведения плавающего окна и его click-through.
- Передача аргументов командной строки, deep links или файлов первому процессу.
- Единственный экземпляр между разными Windows-сеансами или пользователями.
- Автозапуск Windows, updater и полный редизайн tray/lifecycle.

## Декомпозиция реализации

1. `show_main_window` и перевод обоих tray entry points на общий helper.
2. Минимальный guard: mutex, receiver, bounded delivery и ранний вызов в `run()`.
3. Pending-show callback и обработка startup race.
4. Изолированные процессные тесты Windows и negative cases доставки.
5. Пользовательская/архитектурная документация и ручная приёмка debug bundle.

Каждый шаг выполняется отдельной узкой задачей; single-instance модуль нельзя
смешивать с изменением close/minimize semantics.

## Критерии приёмки

- Быстрый двойной запуск оставляет ровно один рабочий процесс Echo.
- Второй процесс не инициализирует logging, settings managers, tray или SSE.
- Повторный запуск показывает скрытое окно, разворачивает свёрнутое и фокусирует
  уже видимое, сохраняя runtime-состояние подключений.
- Запуск до готовности backend/main callback не теряет запрос показа.
- Зависший receiver не удерживает второй процесс дольше 10 секунд.
- Ошибка mutex, receiver или доставки не запускает вторую рабочую копию и
  заканчивается понятной нативной ошибкой.
- После штатного завершения и принудительного kill новый запуск работает без
  очистки файлов или реестра.
- Обычный и повышенный варианты запуска проверены в обеих последовательностях;
  известные ограничения описаны.
- Tray click и tray menu используют тот же helper и сохраняют прежнее поведение.
- На не-Windows target модуль не компилируется и не меняет существующую сборку.

1. Запустить Echo дважды быстро и убедиться, что осталось одно приложение.
2. Повторить запуск при видимом, свёрнутом и скрытом в tray главном окне.
3. Убедиться, что подключения и последние сообщения первого процесса не
   сбрасываются.
4. Повторить запуск во время ранней загрузки приложения.

## Завершение

Выполнено 2026-09-16 по реализации ROADMAP-092 из `app-tts-v2`, но без
переноса настроек сворачивания и других изменений оконного lifecycle.

- Добавлен ранний Windows guard через session-scoped mutex и скрытый receiver
  `WM_COPYDATA`; вызов выполняется до logging, settings и Tauri builder.
- Доставка второго запуска ограничена общим таймаутом 10 секунд и требует
  явного подтверждения wndproc; ошибка никогда не запускает вторую копию.
- Startup race закрыт повторным поиском receiver и pending-show, который
  выполняется после регистрации Tauri callback.
- Tray click, tray menu и повторный запуск используют единый
  `show_main_window`: окно разворачивается, показывается и получает фокус без
  toggle-семантики.
- Вызов Tauri window API вынесен из нативного wndproc в async runtime: ручной
  smoke обнаружил, что синхронный вызов из `WM_COPYDATA` может ждать тот же
  event loop и не восстановить окно.
- Добавлено 7 Windows-тестов single-instance: wide-string encoding, готовый и
  задержанный receiver, pending callback, подтверждение, timeout зависшего
  receiver и отсутствие receiver.
